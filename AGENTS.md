# Repository Guidelines

## Project Structure & Module Organization

- `dfb/`: core backup logic and CLI implementation.
- `dfb/mount/`: experimental mount support (`dfb mount`, optional dependency).
- `tests/`: pytest suite and support fixtures (see `tests/manual_tests.md` for manual cases).
- `docs/`: user and developer documentation, generated CLI reference, changelog, and format/specification docs.
- `utils/`: small helper scripts and one-off utilities.

## Build, Test, and Development Commands

- `python -m pip install -r requirements.txt`: install runtime dependency (`requests`).
- `python -m pip install -e .`: editable install with console scripts (`dfb`, `dfbshebanged`).
- `python -m pip install -e .[mount]`: editable install including optional mount support (`mfusepy`).
- `pytest`: run the test suite (requires `pytest` installed).
- `tests/run_with_cov.sh`: run a focused test subset with coverage HTML output in `htmlcov/`.
- `python build_help.py`: regenerate `docs/CLI_help.md`, `docs/readme.md`, and the autogenerated docs section in `readme.md`.
- `dfb --help`, `dfb mount --help`, or `dfb advanced lsjson-import -h`: quick smoke checks of CLI behavior.

## Coding Style & Naming Conventions

- Code style follows Black; import ordering uses isort with the Black profile (`pyproject.toml`).
- Use 4-space indentation, snake_case for functions/variables, and CapWords for classes.
- Prefer explicit names over abbreviations in public APIs and CLI options.

## Testing Guidelines

- Tests live in `tests/` and follow the `test_*.py` naming pattern.
- Some tests depend on rclone behavior and the sample config in `tests/rclone.cfg`; document any required remotes when adding coverage.
- Manual verification steps belong in `tests/manual_tests.md` when they can’t be automated.

## Commit & Pull Request Guidelines

- Commit history favors short, direct messages (examples: `docs`, `typo`, `Minor: Added /month/`). Keep messages concise and action-oriented.
- PRs should include: a brief summary, tests run (or “not run” with reason), and documentation updates when CLI/user behavior changes.
- If changes affect backup formats or pruning semantics, add a note in `docs/changelog.md`.

## Security & Configuration Notes

- Configuration files are Python and are executed without sandboxing; only run trusted configs and call this out in reviews when editing defaults.

## Documentation Style

- Written documentation uses Markdown; do not hard-wrap text and always leave a blank line after each header.
- New function documentation uses NumPy style and stays concise.
- When changing CLI help text or the docs index, run `python build_help.py` and keep generated files in sync.
- Document agent operations in "codex/TRANSCRIPT.md" with the date and time. This should read like a changelog, usually one-line.
